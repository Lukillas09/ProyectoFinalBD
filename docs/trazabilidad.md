# Trazabilidad: regla → mecanismo → prueba

Entregable de la Etapa 2. Cada regla de negocio de la consigna (RN-01 a RN-15), más la totalidad de la jerarquía de clientes y la excepción de U6, se vincula con:

- el **mecanismo** de PostgreSQL que la protege, con su archivo y el nombre del objeto;
- el **caso de prueba** que demuestra que funciona y que rechaza lo inválido.

La consigna nombra el archivo de pruebas `tests/db_tests.sql`. Este proyecto lo divide por propósito en `db/tests/` (supuesto 17 de `docs/requisitos.md`). `db/tests/run_all.sh` los ejecuta en orden, cada uno con su rol, y termina con código distinto de cero si alguno falla. Cada caso negativo indica en un comentario el error esperado y la prueba verifica el SQLSTATE, la constraint y el mensaje.

Abreviaturas de archivos: `001`…`007` = `db/migrations/00N_*.sql`; `T002`, `T004`, `T005` = `db/tests/00N_*.sql`.

## 2. ¿Dónde va cada regla?

La consigna pide justificar qué herramienta corresponde a cada tipo de regla. El criterio del proyecto es **el mecanismo más simple que protege la regla en todos los accesos**: el de la API, el de `psql` y el de una carga masiva.

| Tipo de regla | Herramienta | Por qué | Ejemplos del proyecto |
|---|---|---|---|
| Valor válido de una sola fila, siempre igual | `NOT NULL`, `CHECK`, `DOMAIN`, ENUM | Declarativo: el motor lo verifica en cada escritura, no se puede olvidar ni saltear y se documenta en el catálogo. | precio > 0, graduación 5..20, CUIT de 11 dígitos, estados como ENUM. |
| Relación entre columnas de la misma fila | `CHECK` entre columnas | Sigue siendo una fila: no necesita consultar otras. | vencimiento > emisión, `total = subtotal − descuento`, fórmula del subtotal del renglón. |
| Existencia de un dato relacionado | `FOREIGN KEY` | Integridad referencial con acciones explícitas (`RESTRICT`, `CASCADE`). | renglón → vino, RN-14 con `ON DELETE RESTRICT`, exclusividad de subtipos con FK compuesta. |
| Unicidad | `PRIMARY KEY`, `UNIQUE` | Índice único: correcto también con escrituras concurrentes. | una cosecha por parcela y campaña, documento del cliente. |
| Depende de otras filas o tablas, o de la fecha actual | Trigger (BEFORE para validar y completar, AFTER para propagar efectos) | Un `CHECK` sólo ve la fila y no puede usar `CURRENT_DATE`, porque cambia con el tiempo y rompe al restaurar un backup. | stock suficiente (RN-09), fecha de confección actual (RN-11), estados (RN-10/11), renglones bloqueados (RN-12), auditoría (RN-13). |
| Invariante que puede pasar por estados intermedios dentro de una transacción | `CONSTRAINT TRIGGER … DEFERRABLE INITIALLY DEFERRED` | Se verifica al confirmar: permite cargar 85 % y después 15 %, o el cliente y después su subtipo. | composición = 100 (RN-05), totalidad de clientes, comprobante con renglones, respaldo de U6. |
| Cálculo que se usa en varios lugares | Función | Una sola definición para triggers, procedimientos, consultas y API. Su volatilidad declarada permite al planificador optimizar sin resultados incorrectos. | `fn_descuento_cliente`, `fn_total_comprobante`, `fn_stock_sala`, `fn_antiguedad_anios`, `fn_recalcular_comprobante`. |
| Operación de varios pasos que debe ser todo o nada | Procedimiento ejecutado en una transacción | Valida, bloquea, modifica varias tablas y cambia el estado como una unidad; si algo falla, no queda nada a medias. | `sp_procesar_ingreso`, `sp_procesar_transferencia`. |
| Quién puede hacer qué | Roles, `GRANT`/`REVOKE`, privilegios por columna, `SECURITY DEFINER` acotado | La API no puede escribir stock, importes, auditoría ni estados: sólo puede usar los caminos que validan las reglas. | `bodegas_rw`, `bodegas_ro`, `007_roles.sql`. |
| Formato, experiencia de usuario y autenticación | API y front | No son integridad de datos; la base sólo devuelve mensajes claros ("RN-XX: …") que la API traduce a HTTP. | Validación de formularios, traducción 409/422/503. |

### Decisiones relevantes para la defensa

- **Las marcas de transacción no son seguridad.** `bodegas.recalculo_importes` y `bodegas.procesando_documento` evitan que el propietario cambie importes o pase un documento a procesado "a mano" por error. Cualquier rol puede fijar una variable propia, así que el límite de seguridad para la API es otro: no tiene `UPDATE` sobre `comprobante`, `ingreso` ni `transferencia`.
- **`SECURITY DEFINER` sólo donde hace falta.** Se usa en las funciones que escriben stock, importes o auditoría, o que bloquean filas (`FOR UPDATE`/`FOR SHARE` exigen privilegio `UPDATE`), y en los cuatro procedimientos. Todas fijan `search_path = bodegas, pg_temp` y ninguna es ejecutable por `PUBLIC` (verificado en `T005`).
- **Las funciones llamadas por un trigger también necesitan permiso.** PostgreSQL no verifica `EXECUTE` sobre la función de trigger al dispararla, pero sí sobre las funciones que ella llama. Por eso `bodegas_rw` tiene `EXECUTE` sobre `fn_validar_transicion_estado`. Lo detectó `T005` al ejecutar un alta de ingreso con el rol de la API.
- **Auditoría con `session_user`.** Dentro de una función `SECURITY DEFINER`, `current_user` es el propietario. `session_user` registra la cuenta que abrió la conexión: con la API, la cuenta de la API. El usuario final no es visible para la base mientras no haya autenticación.
- **`fn_antiguedad_anios` es IMMUTABLE aunque tenga `DEFAULT CURRENT_DATE`.** El valor por omisión se evalúa en la llamada, no dentro de la función (ver el comentario en `003` y el caso del índice rechazado en `T004`).
- **IDENTITY sin `USAGE` sobre la secuencia.** Se comprobó con un alta real en `T005`: la API inserta vinos, clientes, comprobantes y documentos sin privilegios sobre las secuencias.
